## 3. 最初に理解する5つの言葉

**IPアドレス**：通信先のノード・インターフェースを指定するアドレスです。
この環境では一つのnodeが複数のネットワークに接続し、複数のIPを持ちます。

**ポート番号**：そのノード上の、どの通信の受付口へ届けるかを指定する番号です。
実習のサーバーは通常10000で待ちます。クライアントは同じ番号へ送ります。
TCPとUDPは別のプロトコルなので、それぞれでポート10000を使えます。

**ソケット**：プログラムがネットワークと読み書きするための窓口です。
Cではsocket()が返した整数を、その後のreadやwriteなどへ渡します。

**UDP**：メッセージ単位の通信です。接続を確立せずにsendtoで宛先を指定します。
UDP自身は再送・到着順序を保証しません。応答が来なければ今のクライアントはrecvfromで待ち続けます。

**TCP**：接続を確立して使う、順序のあるバイトストリームです。
誤り回復、フロー制御、輻輳制御はTCP側が扱います。
アプリでwriteした一回分の区切りは、受信側のreadにそのまま保存されません。

資料の対応：スライド23〜26。

## 4. 変数が何を表すか

| 変数・値 | 意味 |
|---|---|
| sock0 | TCPサーバーで接続を待ち受けるソケット |
| sock | TCPではacceptでできた一つの接続、またはクライアントの接続用ソケット。UDPでは送受信用ソケット |
| fd | 開いたファイルを表す整数 |
| 0 | 標準入力。read(0, ...)は端末などから読む |
| 1 | 標準出力。write(1, ...)は端末などへ出す |
| buf | 今読み込んだデータを一時的に置く配列 |
| BUF_LEN | 一回のreadで読み込む最大バイト数 |
| n | 今回readで実際に読み込めたバイト数 |
| serverAddr | 相手の宛先、またはサーバー自身の待受アドレスを入れる構造体 |
| clientAddr | acceptやrecvfromが返す相手の情報を入れる構造体 |
| addrLen | アドレス構造体のサイズ。recvfrom/acceptでは結果のサイズも返される |

readの戻り値は、正なら実データのバイト数、負ならエラーです。
通常のTCP受信やファイル読込でreadが0を返すと、データの終わりを表します。
UDPの0バイトデータグラムは受信長0になり得るので、TCPと同じ終了扱いにはできません。

## 5. UDP echoはどう動くか

資料スライド52〜58、65に対応します。

```text
クライアント                               サーバー
標準入力からread                           socket
socket                                     bind（ポート10000）
sendto → 入力したデータを送る ───────────→ recvfrom
recvfrom ← 同じデータを受け取る ←────────── sendto
標準出力に表示
```

サーバーはrecvfromで相手のアドレスを受け取り、そのアドレスへsendtoで返します。
そのため、サーバーはクライアントのIPを起動時に指定する必要がありません。
クライアントは自分のポートを明示的にbindしていませんが、送信時にOSが選びます。

サーバーの画面に受信文字列が表示されるとは限りません。
「echo」は受信したデータを相手へ送り返す動作で、サーバー端末への表示とは別です。

**ホスト名の解決**：getaddrinfoがlocalhostやnode名からアドレスを調べます。
hints.ai_family=AF_INETでIPv4を指定し、UDPではSOCK_DGRAM、TCPではSOCK_STREAMです。
res->ai_addrからsin_addrをserverAddrへコピーして使っています。
コピー後にfreeaddrinfoしているため、コピー先のアドレスはその後も使えます。
この処理は接続や転送そのものではなく、宛先を調べる準備です。

## 6. TCP echoはどう動くか

資料スライド59〜62、66に対応します。

```text
クライアント                         サーバー
socket                               socket
                                     bind
                                     listen
connect ── 接続要求 ───────────────→ accept
write   ── データ ─────────────────→ read
read    ←─ エコー ────────────────── write
close                                close(sock)
                                     次のacceptへ
```

- bind：ソケットに待ち受けるIP・ポートを結び付ける。
- listen：接続を受け付ける状態にする。
- accept：接続を一つ取り出し、通信用の新しいソケットを返す。
- connect：クライアントから接続する。

sock0は受付用、sockは実際の接続用です。sockを閉じてもsock0は残るため次の接続を待てます。
listen(sock0, 5)の5は接続待ちのキューに関係する値です。
5個のクライアントを同時に処理するスレッドを作っているわけではありません。
今のサーバーは一接続の処理が終わってから次のacceptへ進む逐次処理です。

**htons/htonl**：ホストの数値をネットワークのバイト順へ変換します。
ポートは16bitなのでhtons、IPv4の値は32bitなのでhtonlを使う場面があります。
逆方向はntohs/ntohlです。データ本文まで無条件にこれらで変換するわけではありません。

**INADDR_ANY**：自分が持つどのローカルIPv4アドレス宛でも受け付けるための指定です。
相手のIPを指定する値ではありません。

**127.0.0.1 / localhost**：今そのプログラムを動かしているノード自身です。
node2からnode1へ接続したいのにlocalhostと指定すると、node2自身へ接続してしまいます。
現在の構成でnode2からnode1の共有LAN側へ接続する例は172.20.0.10です。

## 7. 実験4-1：echoをどうファイル転送へ変えたか

資料スライド69〜70に対応します。

サーバーは「ソケットから読んだ文字列を返す」処理を、次に変えました。

```c
fd = open(filename, O_RDONLY);
while((n = read(fd, buf, BUF_LEN)) > 0) {
    write(sock, buf, n);
}
```

クライアントは標準出力へ表示する代わりに、保存先ファイルへ書きます。

```c
fd = open(filename, O_CREAT | O_WRONLY | O_TRUNC, 0644);
while((n = read(sock, buf, BUF_LEN)) > 0) {
    write(fd, buf, n);
}
```

これは教材の中心部分を抜き出した例です。実際のコードではwriteが短く戻った場合もnバイト全部を処理するため、内側で繰り返しています。

O_RDONLYは読込専用、O_CREATはなければ作成、O_WRONLYは書込専用です。
O_TRUNCは既存ファイルを空にします。古いファイルが長かった場合に末尾を残さないためです。
0644は8進数の権限指定で、通常は所有者が読み書き、その他は読み取りです。実際にはumaskの影響も受けます。

要求はGETという適当な文字列です。HTTPの実装ではありません。
サーバーは要求された名前を解析せず、自分のargv[1]で指定されたファイルを送ります。
クライアントのargv[3]は保存先の名前です。

ファイルには0バイト値が含まれるので、送る長さをstrlen(buf)で求めてはいけません。
readが返したnバイトをそのままwriteします。
サーバーが送信後にsockを閉じると、受信側は残りを読み終えた後readが0になり、ループを終えます。

## 8. 実験4-2：RTTは何を測っているか

資料スライド71、73〜75に対応します。

```text
start_time取得 → sendto → サーバー受信・返送 → recvfrom完了 → end_time取得
```

差がRTT（往復遅延時間）です。送信方向と返送方向の遅延に、サーバーの処理やOSの待ちも含まれます。
片道時間を直接測っているわけではなく、RTT÷2が常に実際の片道時間になる保証もありません。

```c
rtt = (double)(end_time.tv_sec - start_time.tv_sec)
    + (double)(end_time.tv_nsec - start_time.tv_nsec) * 1e-9;
```

秒の差にナノ秒の差を秒へ換算して足します。
秒の境界をまたぐとナノ秒側の差が負になることもありますが、秒側と合計すれば正しい差になります。
表示をmsにするには秒の値を1000倍します。1msは1000μs、1μsは1000nsです。

入力待ちの前から計ると、人が文字を入力している時間も入ります。
今のコードはsendtoの直前からなので、その時間を含めません。
CLOCK_REALTIMEは教材の例に合わせています。計測中にシステム時刻が変更された場合には影響を受けます。

## 9. 実験4-3 A・B：時間とグッドプット

資料スライド72、74に対応します。

exp43/fclient.cでは次を行います。

1. ホスト名解決・connect・保存先open。
2. start_timeを取得。
3. GET要求を送る。
4. readするたびにファイルへ保存し、nをtotal_bytesへ足す。
5. サーバーが接続を閉じてreadが0になるまで繰り返す。
6. 保存先をcloseし、end_timeを取得。
7. 経過時間とgoodputを計算する。

Timeには要求の送信、サーバーのファイルopen待ち、通信、受信後の書込み、指定した待ち時間などが含まれます。
connectや保存先openは計測開始前です。純粋なネットワーク伝送時間だけではありません。
受信側で測るのは、送信側のwrite完了だけでは受信・保存完了が分からないためです。
writeはまずOSのバッファへ書けた段階で戻ることがあります。

```c
goodput = (double)total_bytes * 8.0 / elapsed;
```

1バイト=8bitなので、バイト数を8倍して秒で割ります。Mbps表示はさらに1,000,000で割ります。
数えるのはファイル本体の量で、TCP/IPヘッダーやACK、GET要求は足していません。

**計算例（実測値ではありません）**：1MiB=1,048,576バイトを2秒で転送すると、
1,048,576×8÷2=4,194,304bps=約4.194Mbpsです。
1MBという表記でも作成方法で実際のバイト数が異なるため、wc -cと実際のnの合計で確認します。

## 10. C：BUF_LENを小さくすると何が起きるか

BUF_LENはアプリの配列の長さ・readで指定する最大量です。
1000から10にすると、同じファイルでも一回に読み出して送る量が小さくなり、呼出回数が増えます。
1MiBを1000バイトずつ読めた場合は1049回で、最後は576バイトです。
100バイトなら10486回、10バイトなら104858回です。

ただし、writeが短く戻った場合、Send countはファイルのread回数より増える可能性があります。
この回数はTCPパケット数ではありません。
TCPはバイトストリームなので、送信側で10バイトを何回もwriteしても、受信側でまとめてreadされ得ます。
受信側BUF_LENも10に変えてしまうと受信側の呼出回数も増えるため、送信側だけの影響を比較したい場合は受信側を1000に固定します。

予想できるのは、呼出回数や処理の負担が増え、性能が変わり得るということです。
「10にしたから速度も必ず100分の1になる」とは言えません。
OSやTCPによる結合・分割、ネットワーク条件にも左右されるので、時間とtcpdumpの両方を確認します。

先生に「送信セグメントを小さくした？」と聞かれたら：

> 資料のヒントに従ってBUF_LENを小さくし、一回のread/writeで扱う上限を小さくしました。
> TCPセグメントの実際の長さがそのままBUF_LENになるとは限らないので、tcpdumpでも確認します。

## 11. D：受信を遅くすると何が起きるか

コードは受信後の処理に次の待ちを入れています。

```c
if(wait_us > 0)
    usleep(wait_us);
```

1000なら1msです。今受信したデータの保存と、次のreadが遅くなります。
そのため、プログラムの受信バッファからデータを取り出す速さが落ちます。

受信アプリが取り出さない間も、しばらくOSの受信バッファへデータは届きます。
バッファの空きが少なくなると、TCPは受信側が受け取れる量を送信側へ伝え、送信を抑えることがあります。
これが受信側に合わせるフロー制御です。ネットワークの混雑に対応する輻輳制御とは区別します。

ただし1MiBがバッファに収まる場合など、送信側のwriteは先に終わり、受信側だけが長時間動くこともあります。
必ずゼロウィンドウが出る、必ず特定の秒数になる、とは断定せずキャプチャで確認します。

待ち時間がある条件のTimeには自分で追加した待ちも入ります。
受信回数N回に毎回1ms待つなら、その待ちだけでおおむねN×1msを要します。
実際のスリープや処理時間は条件によって長くなります。

## 12. tcpdumpで何を見るか

実行コマンドはexp43/README.mdにあります。

- SYNなど：接続を確立する処理。
- データのlength：そのパケットに含まれるTCPデータ長。
- ACK：どこまでのデータを受け取ったかを知らせる応答。
- win：受信側が受け取れる量に関する値。ウィンドウスケーリングにも注意する。
- FINなど：接続を終了する処理。
- 時刻：データやACKがどのくらいの間隔で動いているか。

アプリのSend count/Receive countをパケット数と取り違えないことが重要です。
小さいBUF_LENのときに実際のデータ長やACKの挙動がどう変わったか、
遅い受信のときに通信間隔やwinがどう変わったかを、実測結果として説明します。
localhostでは実験用ノード間の帯域・遅延設定を通らないため、ノード間の結果と区別します。

## 14. 今のコードの範囲・限界も説明する

今のechoやファイル転送は授業の基本的な構成です。
一般向けファイル配信サービス、HTTP、複数接続の同時処理、再接続、UDPの再送処理などは作っていません。
TCP echoは教材と同様に一度のreadで表示するので、大きいデータが分割到着した場合に一回の入力と表示の対応がずれる余地があります。
ファイル転送はEOFまで繰り返すため、受信が分割されても全部保存する構造です。

4-3の単純な方式では、接続の終了とファイルの予定サイズを別々に通知していません。
サーバーで入力ファイルが開けない場合などは相手が接続を閉じ、クライアントは空のファイルを保存して終えることもあり得ます。
そのためエラー表示とcmpを一緒に確認します。
「資料どおりの簡単な方式なので、正しいファイルが全部届いたかは比較でも確認しています」と説明できます。

配布コード由来のコメント・コメントアウトは残しています。
