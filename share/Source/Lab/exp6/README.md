# 実験6：転送処理の改善（BUF_LEN と TCP・UDP の併用）

方針資料（ネットワーク実験_高速化方針.pdf）の「② 転送処理を改善する」の担当分です。
node3 → node1 のファイル転送について、次の2つを比べられるようにしました。

1. **BUF_LEN を変える**：TCP版で、1回の read()/write() の大きさを実行時に `-b` で指定する
2. **TCP と UDP の併用**：データは UDP で決めた速さで流し、開始・再送要求・完了の連絡は TCP で行う

| ファイル | 動かすノード | 役割 |
|---|---|---|
| tcp_send.c | node3 | TCPで送る。`-b BUF_LEN` |
| tcp_recv.c | node1 | TCPで受け取り、時間・グッドプットを表示 |
| hyb_send.c | node3 | UDPでデータ、TCPで制御を送る（併用版） |
| hyb_recv.c | node1 | 併用版の受信。未着分を再送要求（NACK）する |
| udp_relay.c | node4, node5 など | UDPのデータグラムを次のノードへそのまま転送する |
| bench.sh | ホストPC | 受信→送信→cmp→CSV追記を繰り返す測定スクリプト |
| common.h | — | 共通のヘッダ構造体・関数 |

## ビルドとテストファイル

cd /home/ubuntu/share/Source/Lab/exp6

## 1. TCP版：BUF_LEN を変える

実験4-3では `#define BUF_LEN 1000` を書き換えて再コンパイルしていました。
ここでは `-b` で指定します（`1000`、`64K`、`1M` のように書けます。既定は64K）。

```sh
node1$ ./tcp_recv.out -b 64K 20000 /tmp/recv.dat
node3$ ./tcp_send.out -b 64K 172.21.0.10 20000 test100M.dat     # 直接 3→1
node3$ ./tcp_send.out -b 64K 172.27.0.40 20000 test100M.dat     # node4 の relay へ（3→4→5→1）
node1$ cmp test100M.dat /tmp/recv.dat
```

実験4-3（fserver/fclient）からの変更点：

- **送信側から接続して送る**。チームの中継 `relay <待受ポート> <次のIP> <次のポート>` と同じ向きです。
  中継はバイト列をそのまま流せばよく、このプログラム用の特別な処理は要りません。
- **先頭に32バイトのヘッダ**（ファイルサイズ・送信開始時刻）を付けます。
  受信側はファイルサイズ分を受け取ったら終了し、`OK / INCOMPLETE` を表示します。
  4-3の「接続が閉じたら終了」では、途中で切れたことに気付けませんでした。
- **時間は「node3で送信を始めた時刻 → node1で保存し終えた時刻」**。
  同じPC上のコンテナはカーネルの時計を共有しているので、node3の時刻とnode1の時刻を引き算できます。
  中継の接続確立も含みます。
- 転送中は何も表示しません。最後に `RESULT ...` の1行を出します（bench.shが読み取ります）。
- **CPU時間**（user+sys）も表示します。BUF_LENの効果は、グッドプットよりもこちらに出ます（後述）。

## 2. TCP と UDP の併用版

### しくみ

```
node3 (hyb_send)                                      node1 (hyb_recv)
   │── TCP: hello（サイズ, チャンク長, 開始時刻）──────→│  直接回線 3→1（遅延2.5ms）
   │←─ TCP: READY ──────────────────────────────────────│
   │== UDP: [session][seq=0][データ] ==> node4 ==> node5 ==> │  3→4→5→1（50Mbps）
   │== UDP: [session][seq=1][データ] ==> ...              │  指定したレートで送り続ける
   │      ...（全チャンク）                               │  pwrite(seq*chunk の位置)
   │── TCP: ROUND_END ─────────────────────────────────→│
   │                                                      │  UDPが100ms来なくなったら
   │←─ TCP: NACK（未着の seq の範囲）────────────────────│
   │== UDP: 未着分だけ再送 ==>                            │
   │── TCP: ROUND_END ─────────────────────────────────→│
   │←─ TCP: DONE（全部そろって保存した）─────────────────│
```

- ファイルを `chunk` バイト（既定1464）ずつに分け、番号 `seq` を付けて1データグラムずつ送ります。
  1464 = 1500(MTU) − 20(IP) − 8(UDP) − 8(独自ヘッダ) なので、IPの断片化が起きません。
- TCPのように相手の応答（ACK）を待たず、**指定したレートで送ります**。
  tcのtbfはEthernetヘッダ込みの長さで帯域を数えるので、送信側も「データ＋50バイト」で計算しています。
  回線より速く送るとtcのキューからあふれて落ちますが、NACKで再送されるのでファイルは必ずそろいます。
- 受信側は届いた順に関係なく `seq*chunk` の位置へ `pwrite()` し、届いた番号をビットマップで覚えます。
- データ（重い）は速い中継経路、制御（軽い、遅延が効く）は直接回線、と経路を分けています。
- `session` 番号で、前回の転送の残りのデータグラムが混ざっても捨てます。

### 実行例：3→4→5→1 で送る

中継は受信側より先でも後でもよいですが、送信より前に起動しておきます。

```sh
node1$ ./hyb_recv.out 20000 /tmp/recv.dat
node5$ ./udp_relay.out 20000 172.23.0.10 20000      # node5 → node1
node4$ ./udp_relay.out 20000 172.29.0.50 20000      # node4 → node5
node3$ ./hyb_send.out 172.21.0.10 20000 test100M.dat 172.27.0.40:20000@50
#                      ^制御(TCP)の宛先 node1       ^UDPの宛先 node4 と送信レート[Mbps]
node1$ cmp test100M.dat /tmp/recv.dat
```

直接 3→1 だけなら `172.21.0.10:20000@10` を宛先にします（中継は不要）。

| オプション | 意味 |
|---|---|
| `hyb_send -c 1464` | 1データグラムのデータ長。UDP版の「BUF_LEN」にあたる |
| `hyb_send -b 64K` | ファイルを1回に pread() する大きさ |
| `hyb_send -m 100` | 再送を含めた最大の回数。超えたら諦めて終了する |
| `hyb_recv -w 100` | ROUND_END の後、UDPがこのミリ秒来なければ未着とみなす |

### おまけ：複数経路に同時に送る

宛先を複数書くと、**レートに比例してチャンクを振り分けます**（次に送ってよい時刻が一番早い宛先へ送る）。
方針資料3ページの「複数経路の同時転送」にそのまま使えます。
例：資料2ページの最大流の割り当て（C:40, A:10, B:10, D:9）

```sh
node4$ ./udp_relay.out 20002 172.22.0.10 20000      # B: 4→1（Cとは別ポート）
node2$ ./udp_relay.out 20000 172.26.0.50 20000      # D: 2→5（node5の中継はCと共用）
node3$ ./hyb_send.out 172.21.0.10 20000 test100M.dat \
         172.27.0.40:20000@40 172.21.0.10:20000@9.5 172.27.0.40:20002@10 172.24.0.20:20000@9.5
```

A（3→1）は制御のTCPも通るので、少しだけ下げています。

## 3. bench.sh：まとめて測る

**ホストPCで**実行します（`docker exec` で node1・node3 を操作します）。
1回ごとに受信を起動 → 送信 → node1で `cmp` → `results/bench.csv` に1行追記し、最後に平均を出します。
中継（relay / udp_relay）は先に起動しておいてください。

```sh
cd share/Source/Lab/exp6
./bench.sh tcp 172.21.0.10 1000 64K               # 条件A・C（直接）
./bench.sh tcp 172.27.0.40 1000 64K               # 条件B・D（中継）
./bench.sh hyb 172.27.0.40:20000@50 1464          # 併用版（中継）
FILE=test900M.dat REPEAT=5 ./bench.sh tcp 172.27.0.40 1000 64K   # 本番用
```

`FILE`・`REPEAT`・`PORT`・`CTRL`・`SEND_OPTS`・`RECV_OPTS`・`LABEL` を環境変数で変えられます（bench.sh の先頭に説明）。
tcp モードの BUF_LEN は送信・受信の両方に同じ値を指定します。

方針資料4ページの比較条件との対応：

## 動作確認の結果（2026-11-14）

このMacのDockerで5ノードを起動し、`make tc2`（方針資料2ページの調査結果と同じ帯域・遅延）で測りました。
**各1回、5MB/50MBの短い転送なので参考値です。** 本番の数値は100秒以上の転送を複数回測ってください。
TCPの中継は、チームの relay がまだ無いため `nc -l -p P | nc -q 1 次のIP P` で代用しました。

| 経路 | 方式 | 条件 | ファイル | Goodput [Mbps] | 理論上限 |
|---|---|---|---|---:|---:|
| 3→1 直接 | TCP | BUF_LEN 10〜1M（6通り） | 5MB | 9.57（全条件で同じ） | 9.56 |
| 3→1 直接 | UDP+TCP | 10Mbps, chunk 1464 | 5MB | 9.61 | 9.67 |
| 3→4→5→1 | TCP | BUF_LEN 10 / 100 / 1000 / 64K | 50MB | 47.14 / 47.12 / 47.00 / 46.94 | 47.8 |
| 3→4→5→1 | UDP+TCP | 50Mbps, chunk 500 / 1000 / 1464 | 50MB | 44.93 / 47.14 / 47.90 | 45.5 / 47.6 / 48.4 |
| A+B+C+D 同時 | UDP+TCP | 9.5+10+40+9.5Mbps, chunk 1464 | 50MB | 65.91 | 66.7 |

理論上限は「回線の速さ × データ ÷ (データ＋ヘッダ)」で、
TCPは 1448/1514、UDP併用版は chunk/(chunk+50) です。全条件で `cmp` 一致を確認しています。
（tbfは最初にburst分だけ制限なしで通すので、短い転送では理論上限をわずかに上回ることがあります。）

BUF_LEN と CPU時間（user+sys、送信側 / 受信側）：

| BUF_LEN | 3→1, 5MB | 3→4→5→1, 50MB |
|---:|---|---|
| 10 | 0.383 / 0.717 s | 2.261 / 2.790 s |
| 100 | 0.061 / 0.148 s | 0.463 / 1.013 s |
| 1000 | 0.016 / 0.071 s | 0.182 / 0.478 s |
| 64K | 0.010 / 0.064 s | 0.069 / 0.343 s |

## わかったこと・注意

- **TCPでは BUF_LEN を変えてもグッドプットは変わりませんでした。**
  10Mbps・50Mbpsの回線ではネットワークが先に上限になり、BUF_LEN=10 でもCPUが追いつくためです。
  効果は read/write の回数とCPU時間に出ます（中継経路・50MBで、1000 → 64K にすると送信側が 0.18 → 0.07秒）。
  実験4-3で「1/30に低下」したのは localhost（帯域制限なし）でCPUが上限だったためで、条件が違います。
  比較実験の条件Cは「グッドプットはほぼ同じ、CPU時間は減る」という結果になる見込みです。
- **UDP併用版ではチャンク長がそのまま効きます。** UDPは1データグラム＝1パケットなので、
  小さいとヘッダの割合が増えます。TCPはOSが小さな write をまとめて送るので、この差は出ません。
- **単一経路では、UDP併用版の上積みは約2%です**（47.1 → 47.9Mbps）。パケットロスが設定されておらず、
  TCPもほぼ回線の上限まで出るためです。差はヘッダが小さい分（TCP 32+20 / UDP 16+20 バイト）です。
  併用版が大きく効くのは複数経路のときで、4経路で 65.9Mbps（TCP中継の約1.4倍）でした。
  経路ごとにレートを決めて振り分け、受信側は番号で組み立てるだけなので、TCPの接続を経路ごとに管理するより簡単です。
- **最初の1回だけ、中継で数十個落ちることがあります。** 中継ノードが次のノードのMACアドレスを
  ARPで調べている間（往復20ms）に、待たされたパケットがあふれるためです（NACKで回復します）。
  測定前に1回転送するか、各ノードで次のノードへ `ping -c 1` しておくと条件がそろいます。
- 受信ファイルは `/tmp` に書いてください。`share` はホストPCとの共有フォルダで、書き込みが遅れることがあります。
  UDPは受信が遅れると受信バッファ（一般ユーザーでは約416KB）からあふれて落ちます。
- UDP併用版には輻輳制御がありません。**レートは自分で回線に合わせて指定します**（このネットワーク専用の方式です）。
  回線の速さより大きくしても、tcのキュー（1000パケット）に収まる間は落ちません。
  ロスが出たら `round 1: ... missing` の割合を見てレートを下げてください。
- チームの relay にも BUF_LEN があれば、条件B/Dではそちらも合わせて記録してください。
