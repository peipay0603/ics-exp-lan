# 実験4-4・4-5・5の実行手順

配布コードのコメントとコメントアウトは残しています。
4-4はSource/udp_echo_client_ep.cのepollの流れをLab側へ取り込み、
実際のstdin EOF処理と受信エラー処理を加えています。

## ビルド

Dockerノードで：

```sh
cd /home/ubuntu/share/Source/Lab
make
cd /home/ubuntu/share/day2
make
```

## 実験4-4：入力待ちと受信待ちを分ける

node1：

```sh
nc -u -l -p 10000
```

node2：

```sh
cd /home/ubuntu/share/Source/Lab
./lab_udp_ecli_ep.out 172.20.0.10 10000
```

1. node2側でhelloなどを入力する。
2. node1側に届いたことを確認する。
3. node1側からreply1と入力し、node2側に出ることを確認する。
4. node2では何も入力せず、node1からreply2を送る。
5. reply2もnode2に出れば、標準入力待ちに妨げられず受信できている。
6. node1からquitを送るとクライアントを終了できる。ncはCtrl+Cで終了する。

コードはepoll_createで監視用の窓口を作り、epoll_ctlで標準入力0とsockを登録します。
epoll_waitが返すeventsのfdを見て、入力ならread→sendto、ソケットならrecvfrom→表示を行います。
stdinがEOFになったら監視から外し、ソケットの受信は続けます。
UDPなので最初の送信まではOSが自分の送信元ポートを割り当てていません。最初に一度入力してください。

node1：


node2：

```sh
./lab_udp_ecli_ep.out 172.20.0.10 10001
```

node3：

```sh

```

各クライアントで最初にjoinなどと入力します。最初に送ったアドレスが参加者として登録されます。
その後の文字列は参加者全員に転送されます。自分にも返ります。
一方が入力している最中でなくても、他の参加者からの発言を表示できます。

最大16クライアントです。UDPなので、配信の再送や到着順保証は実装していません。

## 実験5-1：Raw UDP

node2のターミナル1：

```sh
nc -u -l -p 10000
```

node2のターミナル2：

```sh
sudo tcpdump -i any -nn -vvv -X 'udp src port 10000 and dst port 10000'
```

node1：

```sh
cd /home/ubuntu/share/day2
sudo ./raw-udp-client.out 172.20.0.10 172.20.0.20
```

文字列を入力してEnterを押すとIPヘッダー・UDPヘッダーを組み立てて送ります。
終了はCtrl+Dです。受信側ncとtcpdumpはCtrl+Cで終了します。

穴埋めした値：

| 項目 | 値・式 | 意味 |
|---|---|---|
| ip_v | 4 | IPv4 |
| ip_hl | sizeof(struct ip)/4 | 20バイトなら5。32bit単位 |
| ip_ttl | 64 | 通過できるホップ数の上限 |
| source・dest | htons(10000) | UDPの送受信ポート |
| ip_len | htons(totalLength) | IPヘッダーを含む全長 |
| UDP len | htons(sizeof(struct udphdr)+len) | UDPヘッダー8バイトと本文 |

配布されたchecksum関数自体は変更していません。
連続送信でもチェックサムを正しく求められるよう、計算前にチェックサム欄を0に戻しています。
IPヘッダーの未設定領域が不定にならないよう、パケットバッファも最初に0で初期化しています。
IPPROTO_RAWは通常のUDPソケットと異なり、IPヘッダーから自分で組み立てるので管理者権限が必要です。
