# 最終課題：経路改善による高速ファイル転送

node3 から node1 へのファイル転送を、次の3つを組み合わせて高速化するプログラム一式です。

1. **速い経路の利用：** 中継（スプリットTCP）で直接より速い経路を使う
2. **複数経路の同時利用：** 最大流で選んだ複数の経路から同時に受け取る
3. **速度による経路変更：** 転送中に経路ごとの速度を測り、遅くなった経路を外し、速くなった予備経路に乗り換える

方針共有資料の STEP 1（経路探索＋逐次中継）、STEP 3（複数経路の同時転送）、「ほかに検討したアイデア」の「転送中の戦略変更」「到着時間を予測して分配」「転送終盤の再割り当て」に当たります。

## 構成

| ファイル | 実行するノード | 役割 |
|---|---|---|
| `collect_links.sh` | 全ノード | 自ノードから出るリンクの帯域（tbf）と遅延（netem）を調べ、`links/nodeN.txt` に書く |
| `routeplan.py` | どこでも | リンク表から経路を決め、各ノード用の起動スクリプトを `plan/` に生成する |
| `fserver.out` | node3 | ファイルサーバ。範囲要求（`GET off len`）に `sendfile()` で応える |
| `relay.out` | node2, 4, 5 | 中継。受け取った分から次々に転送する（逐次中継、スプリットTCP） |
| `fclient.out` | node1 | 複数経路から同時にチャンクを取りに行き、`pwrite()` で組み立てる。転送中に速度を測って経路を入れ替える |
| `sim/` | — | Docker なしでネットワークを再現して試すスクリプトと結果 |

`share` は全ノードで共有されているので、ビルドもスクリプトの生成も1か所で済みます。

## 使い方（実験環境）

```sh
# どこか1つのノードで（share は共有）
cd /home/ubuntu/share/final
make
make test.dat SIZE=900          # 900 MiB（本番は100秒以上になるサイズに）

# 1. ネットワーク調査：node1〜node5 それぞれで1回
./collect_links.sh

# 2. 経路の決定：どこか1つのノードで
python3 routeplan.py            # 複数経路（最大流）＋予備経路
# python3 routeplan.py --mode single     最良の単一経路から始める（ほかは予備経路）
# python3 routeplan.py --path 3-4-5-1    経路を手で指定（比較実験用）
# python3 routeplan.py --standby-hops 0  予備経路なし

# 3. 各ノードで起動（表示された順に。node1 は最後）
./plan/node3.sh                 # node3: サーバ
./plan/node4.sh                 # node4: 中継（node2, node5 も同様）
./plan/node1.sh                 # node1: クライアント（time -p 付き）
                                # 経路を固定して比べるときは plan/node1.sh のコマンドに -S を付ける

# 4. 確認と後片付け
md5sum test.dat received.dat    # 2つが一致すること
./plan/stop.sh                  # 各ノードで fserver/relay を止める
```

== 予備経路（6 本．転送中にプローブして 5.0 Mbps 以上出れば使い始める）

経路は `IP:PORT[xN][/dD][@Mbps][=名前]` の形で書きます（`xN` は接続数、`/dD` は先出し数、`@Mbps` は計画上の速度、`=名前` は表示用の名前）。`-s` を付けた経路は予備経路です。

## 仕組み

### 1. 調査（collect_links.sh）

`ip -o -4 addr` で `172.2X.0.N0` 形式のアドレスを探し、自分のノード番号と各インタフェースの接続先を判定します（サブネット X がどのノード間のリンクかは docker-compose.yml の定義どおり）。
次に `tc qdisc show` で、送信側に設定された tbf の rate と netem の delay を読みます。
帯域制限は送信側のインタフェースにかかっているので、**データの向き（3→4 と 4→3）を区別**して記録します。

調査済みの tc2 の値は `links_tc2.txt` にあります（`--links links_tc2.txt` で使えます）。

### 2. 経路の決定（routeplan.py）

- **単一経路：** node3→node1 の単純経路をすべて列挙します。ボトルネック帯域が最大のものを選び、同じなら遅延の合計、次にホップ数が小さいものを選びます。tc2 では 3→4→5→1（50 Mbps）で、直接（10 Mbps）の5倍です。
- **複数経路：** Edmonds-Karp 法で最大流を求め、その流量を「流せる量が最大の経路」から順に経路へ分解します。流量が `--min-mbps`（既定 5）未満の経路は使いません。
- **先出し数：** 経路ごとに往復遅延（RTT）を計算し、その間に流れるデータ量（BDP）の1.5倍を先に要求できるよう、要求の先出し数を決めます。遅延の大きい経路（例：tc1 の 4→1 は片道 250 ms）では、`IP:PORT/d19` のように経路別の値を付けます。
- **予備経路：** 計画に入らなかった3ホップ以下の経路（tc2 では6本）も中継を起動しておき、クライアントに `-s` で渡します。今は遅くても、転送中に設定が変わって速くなれば使えるようにするためです。
- **起動スクリプト：** 経路 k の中継はポート `20000+k` で待ち受けます。接続はクライアントから逆向きに、各リンクの**直結サブネットのアドレス**へ張ります。経路を変えるのにルーティング設定は一切変えません。

例：経路 3→4→5→1（データの向き）の場合、接続は次の順に張られます。

```
node1 ──→ 172.23.0.50:20001 (node5 relay) ──→ 172.29.0.40:20001 (node4 relay) ──→ 172.27.0.30:10000 (node3 fserver)
```

データは 3→4（50M）、4→5（50M）、5→1（50M）の各リンクを、帯域制限のかかる送信方向に流れます。

### 3. 中継（relay.c）：スプリットTCP・逐次中継

受け付けた接続ごとに fork し、次のノードへ新しい TCP 接続を張ります。両方向を2つのスレッドでそのまま転送します。

- ファイル全体を待たず、受け取った分（最大 256 KiB）から次へ送ります。中継による待ち時間は1回の read 分だけです。
- TCP 接続が区間ごとに分かれるので、各区間の RTT は短く、輻輳制御や再送も区間内で完結します。
- 中身を解釈しないので、**実験4-1（exp43）の fclient/fserver もそのまま中継を通せます**（比較条件 B）。

### 4. サーバとクライアント（fserver.c, fclient.c）

| 工夫 | 内容 |
|---|---|
| 動的なチャンク割り当て | ファイルを 256 KiB に分け、空いた接続が次のチャンクを取りに行く。速い経路ほど多く運ぶので、割合を事前に決めなくても最大流の比率に近づく |
| 要求の先出し（パイプライン） | 1接続あたり既定4個まで要求を先に送り、往復待ちの空き時間をなくす（256 KiB × 4 = 1 MiB） |
| 終盤の重複要求 | 未要求のチャンクがなくなったら、遅い経路で受信中のチャンクを空いた十分速い経路でも取りに行き、先に届いた方を採用する |
| 経路障害への対応 | 接続が切れたら、その接続が受信待ちだったチャンクを他の経路に割り当て直し、接続を張り直す（5回失敗したらその経路は使わない） |
| sendfile / pwrite | ファイル→ソケットのコピーをカーネル内で行う。受信側は到着順に関係なく正しい位置へ書く |
| TCP_NODELAY | 小さな要求メッセージを Nagle アルゴリズムで待たせない |

### 5. 速度による経路変更（fclient.c の監視スレッド）

動的なチャンク割り当てだけでも、使っている経路の中では速い経路に多く割り当てられます。しかし、**最初に決めた経路の外には出られません**。転送中にネットワークの設定が変わって別の経路が速くなっても、それを使えません。そこで、監視スレッドが 0.5 秒ごとに次のことを行います。

| 動作 | 内容 |
|---|---|
| 速度の測定 | 経路ごとに受信量から速度を求め、指数移動平均（EWMA）で平らにする。受信待ちのない間は測らない（終盤の待ちを遅さと誤解しないため） |
| 降格 | 使用中の経路が `-m`（既定 5 Mbps）未満の状態が2秒続いたら予備に回す。受信待ちのチャンクはすぐ他の経路に回し、接続は張り直す。最後の1本は降格しない |
| プローブ | 予備経路には3秒ごとに1チャンクだけ要求し、最初の 64 KiB の受信速度を測る（往復時間の影響を除くため、最初の1バイトが届いてから測る）。遅ければ残りを待たずに打ち切り、チャンクは他の経路に回す |
| 昇格 | プローブの速度が `-m` 以上なら使用中に戻す（または新しく使い始める） |
| 到着時間の予測 | 残りが3秒分を切ったら、「自分がこのチャンクを受け取り終える時刻」と「全経路で残りを受け取り終える時刻」を比べ、自分の方がずっと遅いなら新しいチャンクを取らない（最後に遅い経路を待たないため） |

`-S` を付けると、これらを行わずに経路を固定します（比較用）。

経路の入れ替えは、次のように記録されます（tc2 で計画し、5秒後に tc3 に切り替えた例）：

```
[network changed to tc3 at about 5s]
[  6.51s] path 3-2-1    172.20.0.20:20005    standby -> active (probe 34.36 Mbps)
[  7.51s] path 3-2-5-1  172.23.0.50:20004    active -> standby (0.54 Mbps < 5.0)
[  8.51s] path 3-4-5-1  172.23.0.50:20001    active -> standby (1.49 Mbps < 5.0)
```

## 結果（Docker なしの再現環境）

`sim/sim_mesh.sh` で network namespace を使って tc2 のネットワークを再現し、`sim/run_conditions.sh` で比較実験を行いました。

**注意：** このマシンのカーネルでは netem（遅延）が使えないため、**帯域制限だけで遅延なし**の再現です。実験環境では遅延が加わるので、特に B・D・E は下の値より下がる可能性があります。本番前に実験環境で測り直してください。

100 MiB（104,857,600 B）、すべて md5 一致。時間はクライアントを起動してから終了するまで（`time -p` と同じ測り方）：

| 条件 | 内容 | 時間 [s] | スループット [Mbps] | 理論上限 | 基準比 |
|---|---|---:|---:|---:|---:|
| A | 変更なし（exp43 で直接 3→1） | 87.72 | 9.56 | 10 | 1.0 |
| B | 経路だけ変更（exp43 ＋ relay で 3→4→5→1） | 17.59 | 47.70 | 50 | 5.0 |
| C | プログラムだけ変更（新 fclient で直接 3→1） | 87.75 | 9.55 | 10 | 1.0 |
| D | 両方変更（新 fclient で 3→4→5→1） | 17.68 | 47.43 | 50 | 5.0 |
| E | 複数経路（最大流の 4 経路＋予備 6 経路、速度による経路変更あり） | 13.12 | 63.93 | 69 | 6.7 |
| E2 | 1 Mbps の 2 経路も最初から使う | 12.94 | 64.84 | 71 | 6.8 |

分かったこと：

- **経路の変更が支配的です。** 10 Mbps の直接リンクでは、プログラムを改善しても回線の上限（9.56 Mbps、TCP/IP ヘッダを除くと上限の約96%）で頭打ちになりました（A = C）。中継で 50 Mbps の経路に変えると5倍になりました（B）。
- **D と B がほぼ同じ**なのは、どちらも回線の上限で決まっているためです。プログラムの工夫（sendfile、大きな単位）は、回線が速いか CPU が遅い場合に効いてきます。
- **複数経路では理論上限 69 Mbps の約93%** が出ました。経路ごとの内訳（約58%、14%、14%、14%）は最大流の割り当て（40:10:10:9）とほぼ一致し、動的な割り当てで自然に最大流の比率に近づくことを確認しました。
- **1 Mbps の経路を加えても、ほとんど変わりません**（+0.8 Mbps）。終盤の重複要求があるので遅い経路が足を引っ張ることはありませんが、手間に見合わないので既定では使いません。
- **チャンクは小さめが有利でした**（`sim/results/sweep.txt`）。4 MiB では終盤に遅い経路の残りを待つ時間が長く、47.7 Mbps まで落ちました。256 KiB を既定にしています。
- **経路障害：** 転送中に経路 3→4→1 の中継を止めても、残りのチャンクが他の経路に割り当て直され、ファイルは正しく届きました（58.3 Mbps）。

他の設定でも `routeplan.py` は経路を選び直します（start1：3→4→1 と 3→2→5→1 で 99 Mbps、start3：3→2→1 ほかで 70 Mbps、start4：3→2→5→1 ほかで 69 Mbps）。

### 転送中にネットワークの設定が変わる場合（`sim/run_change.sh`）

経路は最初の設定（tc2）で決め、転送開始から5秒後に tc3 または tc4 に切り替えました。100 MiB、すべて md5 一致：

| 方式 | 変更なし（tc2 のまま） | tc2 → tc3 | tc2 → tc4 |
|---|---:|---:|---:|
| D 単一経路・固定（3→4→5→1、`-S`） | 47.67 Mbps | 120秒で終わらず | 12.48 Mbps |
| G 単一経路から始めて速度で経路変更 | 61.96 Mbps | 58.79 Mbps | 62.09 Mbps |
| E 複数経路・固定（最大流の4経路、`-S`） | **64.80 Mbps** | 27.67 Mbps | 62.67 Mbps |
| F **複数経路＋速度による経路変更** | 63.65 Mbps | **60.29 Mbps** | **63.78 Mbps** |

tc2 → tc3 は3回繰り返し、F は 58.4〜60.4 Mbps、E は 27.3〜27.9 Mbps でした（`change_tc2_to_tc3/repeats.txt`）。

分かったこと：

- **設定が変わると、経路を固定した方式は大きく遅くなります。** tc3 では、計画した経路のうち 3→4→5→1 と 3→2→5→1 が 1 Mbps 程度に落ちます。固定の複数経路（E）は残った 3→1 と 3→4→1（各 10 Mbps）に頼るしかなく、27.7 Mbps になりました。固定の単一経路（D）は120秒以内に終わりませんでした。
- **速度による経路変更を組み合わせると（F）、変更後も約60 Mbps を保ちました**（E の 2.2 倍）。設定が変わってから 1.5 秒後に予備経路 3→2→1（tc3 では 50 Mbps）を昇格させ、遅くなった2本を 2.5〜3.5 秒後に降格させています。
- **単一経路から始めても（G）、プローブで他の経路を見つけて使い始めます。** 2秒以内に、最大流と同じ4経路の組み合わせにたどり着きました。そのため、計画が単一経路でも約62 Mbps が出ます。
- **設定が変わらないときのコストは小さいです。** F は E より 1.8% 遅いだけでした（プローブで 1 Mbps の経路にチャンクを少し割り当てるため）。
- **tc4 では差が小さくなります。** tc4 で速くなる 3→2→5→1 が、もともと計画に入っているためです。動的なチャンク割り当てだけで、速くなった経路に多く割り当てられます。
- **誤った昇格は自動で戻ります。** 設定の切り替え直後に、実際は 1 Mbps の経路がプローブで 47 Mbps と測られて昇格したことがありました（中継に溜まっていたデータを測ったため）。この経路は数秒後に降格され、転送は正しく終わりました。

**再現環境の注意：** `tc qdisc replace` で tbf の設定を転送中に置き換えると、キューに残った大きな（GSO でまとめられた）パケットが新しい burst より大きい場合に、そのリンクが止まったままになることがありました。`sim_mesh.sh apply` では、qdisc をいったん消してから作り直しています。

```sh

```

## 本番に向けた注意

- 本番は100秒以上になるサイズにします。69 Mbps なら約 900 MB 以上が必要です（`make test.dat SIZE=900`）。
- 実験環境の遅延（3→4→5→1 で RTT 約 60 ms）があると、TCP のウィンドウが育つまで時間がかかります。そのため、ファイルが大きいほど上限に近づきます。
- `collect_links.sh` は自ノードの tc 設定を読みます。「本当のネットワークで動かす想定」と見なされない場合は、iperf3 などで測った値を `links/nodeN.txt` に同じ形式で書けば、そのまま `routeplan.py` に渡せます。
- 予備経路のプローブは、3秒ごとに1本ずつ 256 KiB のチャンクを要求します（遅ければ 64 KiB で打ち切ります）。実験環境の遅延が大きい経路では、最初の1バイトが届くまでの時間は速度の計算に含めないので、遅延だけで誤って降格・未昇格になることはありません。
- 昇格・降格のしきい値は `-m`、プローブの間隔は `-p` で変えられます（`plan/node1.sh` のコマンドを編集）。
- 4-1 の基準（BUF_LEN=1000 の exp43）との比較は、`--path 3-1` / `--path 3-4-5-1` で生成した `plan/node1.sh` のコメントにある exp43 のコマンドで行えます。
